# Owner retention review and removal

## Current scope
The Records and health page calculates review dates and supports holds. Owner-confirmed removal supports expired unconverted wizard inquiries and expired unlinked imported email copies. It is not an automatic purge and is not complete anonymization of every related system.

Removal is blocked for holds, unexpired records, proposals, preparation, imported-mail sources, confirmed/completed/progressed events, operations history/reservations or unresolved notification jobs. Completed-event financial records and Gmail imports stay in the separate review procedure below. Do not force these through the inquiry removal endpoint.

## Eligible inquiry procedure
1. In Records and health, open the record and verify its identity against the event desk. Check no event conversion, dispute, audit, insurance claim or required-record obligation applies. Apply a hold with a short reason if any do.
2. Save the review and refresh. Confirm it is Review due. Inventory sent email, exports, clipboard/download copies and backups; removal from the active database does not erase those copies.
3. Only an authorized owner can type `REMOVE <exact ID>`, confirm the separate-copy review, and submit Remove expired inquiry. The server rechecks eligibility and both record/review versions inside a database transaction, including locks on PostgreSQL. Stale edits or new holds stop removal.
4. The active inquiry content and completed notification jobs are removed. A minimal receipt tombstone, existing submission-key/fingerprint metadata and disposal audit (ID, timestamp, owner) remain to prevent stale updates and duplicate resubmission from restoring the record. These retained identifiers are pseudonymous, not a promise of complete anonymity.
5. Verify the inquiry no longer appears in active lists. Record outside-copy handling through the appropriate systems. No customer email is sent by this operation.

## Imported Gmail copies
Review at 90 days. Preserve any copy needed for an active event or obligation; apply a hold. Removal must preserve the Gmail source, prevent reimport and check thread-to-event links and simultaneous conversion. In Records and health, choose Imported email copies, save a review, refresh, then explicitly confirm removal. The transaction locks the copy and its review, checks age/hold/version and rejects any event linked to the message or thread. Event creation locks the same source copy before insertion; removal and conversion cannot both commit. The message ID, removal timestamp and actor remain as minimal reimport-prevention/audit metadata; sender, subject, body, extracted payload and thread ID are removed from the active copy. The Gmail source is unchanged. This is owner-reviewed removal, not an automatic 90-day purge. Gmail itself follows the organization's mail policy, separately from imported dashboard copies.

## Completed-event core records
Review seven years after the later of financial closeout and relevant tax filing/due date. Verify closeout/payment status and retain required contracts, invoices and accounting/insurance evidence for any longer obligation. Map all copies first: inquiry payload/history, proposals/acceptances, preparation, operations event data/audit, purchasing/reservation references, imported email, exports and backup snapshots. The separate Retire eligible event control requires stage 8, complete actuals, zero client balance, paid supplier receipts, no active stock commitments, an expired seven-year review period, matching versions, cleared obligations and outside-copy confirmation. It removes the inquiry payload/proposal/preparation/history and event-linked operations, receipts, reservations and audit details in one transaction. Aggregate financial totals, record IDs and receipt fingerprints remain; shared staff/inventory records and stock quantities remain unchanged. This is scoped personal-detail retirement, not complete anonymity. Gmail-sourced events remain blocked for coordinated review; do not force them through this control. Independently copied details in shared notes, exports or source Gmail must be handled separately.

## Backup and restore
Active removal does not erase existing Cloud SQL snapshots or sent emails. Let backup copies expire according to the configured schedule and preserve the disposal ledger independently before any restore. After restoring an older database, compare/reapply verified disposal records before enabling traffic; do not resurrect removed inquiries. Test this restoration reconciliation in isolation before production. Use the owner-only Download removal ledger for recovery link after each removal and store the restricted export outside the database backup set. Run scripts/reconcile-restored-database.mjs only against an isolated restored database, with BARSYS_RESTORE_ISOLATED=confirmed-offline and its dedicated BARSYS_RESTORE_DATABASE_URL. The tool rejects runtime DATABASE_URL, validates the reviewed ledger, transactionally reapplies removals/retirements, clears sessions and quarantines pending/sending deliveries. Conflicting links or a restore preceding financial closeout cause rollback; keep the target offline for review. This is an explicit operator workflow, not scheduled reconciliation. Verify export freshness before releasing any restored target.

## Validation / release boundary
Tests use synthetic databases only; no real inquiry or Gmail source is removed. See qa/mail-retention-2026-09-10.md for current release verification. Use PRIVACY-OPERATIONS.md for copy review, the independent ledger archive and case closure; launch decisions must cite current review evidence.
